# PZ Worker V3.2 unified candidate — REVIEW ONLY

This is a **review candidate**, reconstructed from the uploaded Staging V3.1 worker and adapted so Production and Staging can share the same JavaScript source with isolated Cloudflare bindings and secrets.

**Do not deploy to Production and do not merge this branch into main.** This file is for browser viewing/copying because the chat attachment download repeatedly failed.

## Storage bindings (names shared, resources isolated)
- `DB`: Staging `pz-staging-db`, Production `1`
- `PRODUCT_IMAGES`: Staging `pz-staging-images`, Production `pz-product-images`
- `SITE_CONFIG_KV`: use each environment's own namespace
- `SITE_CONFIG_HISTORY`: Staging history bucket / Production `pz-site-config-history`
- `JWT_SECRET`: separate secrets; do not migrate passwords or tokens

## What was changed
1. Image URL used by uploads and site configuration publishing now follows environment variable instead of always using the production CDN.
2. The allowed image file types are limited to JPEG, PNG, WebP, checked by magic header and MIME.
3. R2 object upload keys receive UUID suffixes to reduce collisions.
4. Staging does not accept the Production CDN hostname; Production accepts only `cdn.peng-zhan.com`.

## Deployment safety
- GitHub branch is independent from Production `main` and existing PRs; committing this file has **not** deployed either Worker.
- This code must be validated using Cloudflare Staging, including login, permissions, product lifecycle, batch uploads, config publishing, image uploads and inquiries.
- Even after tests pass, production migration requires checking users/roles, bindings, API routing, existing published products and rollback plan.
- The existing public legacy KV snapshot is not suppressed by setting `PZ_CATALOG_V2_ENABLED=false`; old content may remain visible until a separate switch is planned.
- Static reconstruction does not replace source-level tests, staged deployment, security audit, or rollback exercise.
